# Design brief — `open-source-documentation-writer`

- **Domain:** Documentation
- **Meets all stated requirements:** True
- **Chosen anchor:** `simplestViable`
- **Reversibility:** `two-way`
- **Rationale:** Nothing machine-parses README and the checklist's tests only match strings, so prose layout, table shape and catalogue-table or drift-test additions can be revisited when a requirement arrives. The one costly-to-change element, existing checklist step IDs and test-pinned strings, is preserved by appending, and running R28 last keeps its measured snapshot from becoming a temporary solution inside this plan's horizon.
- **Confidence:** 77

## mostDurable

**Description.** Make the same corrections but remove the drift-prone duplication. The pin table names each file's pinning identifiers (_ENABLED_CHART_COUNT, _ENABLED_KEYS_IN_ORDER, _SIN_CHART_KEYS, ...) and what breaks, with no literal values, and tells the reader to measure with enabled_specs()/all_specs(), mirroring CLAUDE.md's rule. Warning counts are stated as a formula (one per enabled SERIES chart plus one per scalar source file, per scenario-deck), with the current value given once. The quality-gate section states the contract (four commands exit 0, coverage at or above the 85% floor, chunked invocation, about 9 minutes) and a snapshot labelled with the commit it was measured on. A per-level chart catalogue table in SPECS order (key, UI title, unit, selector) makes CLAUDE.md's claim true. A static docs-drift test pins README counts and the catalogue table to the registry, and the new checklist section gets a static test following the existing test_renderer_contract.py / test_charts_filters.py pattern. Optionally, README is split into Diátaxis pages under docs/ (reference: configuration, catalogue; how-to: extending the catalogue; explanation: divergences, units).

**Costs.** A larger README rewrite and a 31-row hand-maintained table, which becomes a new drift point unless a generator or drift test backs it. A new test module and its maintenance, which belongs to the test-strategist seat. Every chart change in future plans gains a docs-test failure to fix. A docs/ restructure would exceed R24/R28 scope, since the operator asked for matching docs, not drift-proofing or reorganisation. Most of this is not traceable to a stated requirement, so it risks the over-engineering failure in the Cleanliness Bar.
